# LinkedIn Post Structures

<!-- playbook-section:universal -->
Post structures are macro layouts. They decide the shape of the complete post,
while body frameworks decide how the argument progresses inside that shape.
Templates are scaffolds, never public labels or scripts.

Use only as much structure as the source supports. Do not pad a thin source to
hit a length target. Preserve one core argument from opening through close.

Proof rules override every template:

- bracketed examples are placeholders, not facts;
- numbers and named outcomes require source evidence or Approved Evidence;
- first-person story details require Founder Experience or supplied Trend
  Reaction language;
- a TrendCard alone cannot become a founder case study;
- resource delivery language requires an active approved Content Resource.
<!-- /playbook-section -->

<!-- playbook-section:selection -->
Select one macro structure:

- `comprehensive_breakdown` for a process, system, or framework with enough
  source depth for several supported sections;
- `listicle` for a small ordered set of criteria, lessons, checks, or steps;
- `case_study_before_after` only when the source provides real before, change,
  and after states;
- `conversational_story` for one moment, observation, reaction, or focused POV.

Compatibility guidance:

- Founder Experience: any structure when its documented details support it.
- TrendCard: breakdown, listicle, or conversational story; case study only when
  Approved Evidence independently supplies a real case.
- Trend Reaction: conversational story is the default; use a list or breakdown
  only when the reaction contains multiple substantive implications.
- Resource post: choose the structure that teaches the problem first. Do not
  turn the entire body into a resource advertisement.

Choose the smallest structure that fully carries the argument.
<!-- /playbook-section -->

<!-- playbook-section:comprehensive_breakdown -->
## Comprehensive Breakdown

Best for systems, process architecture, decision models, and detailed
how-it-works posts.

Use this sequence:

1. Hook with the core claim or root tension.
2. Brief context: why the issue matters to this ICP now.
3. Preview the model without overselling it.
4. Develop three to five source-supported sections.
5. Show dependencies, handoffs, failure points, or decision rules.
6. End with the practical implication and optional planned CTA.

Useful body shapes:

```
[Core claim]

[Why this matters to the target buyer]

[Section 1: the first layer]
[Specific explanation or check]

[Section 2: the second layer]
[Specific explanation or check]

[Section 3: where it breaks]
[Specific explanation or check]

[Takeaway]
[Optional CTA]
```

Quality rules:

- each section must advance the argument, not repeat it;
- headings may be plain text, but avoid noisy all-caps scaffolding;
- include only the number of sections the source earns;
- connect steps explicitly when the value is in the handoff;
- prefer a shorter listicle or conversational post when the source has fewer
  than three substantive parts.
<!-- /playbook-section -->

<!-- playbook-section:listicle -->
## Listicle

Best for lessons, criteria, checks, operating rules, and compact frameworks.

Use this sequence:

1. Hook with the argument, not "here are some tips."
2. Explain why the list matters to the target buyer.
3. Present three to six ordered points when the source supports them.
4. Give each point a clear name and a practical explanation.
5. Synthesize the list into one decision rule or takeaway.
6. Add the planned CTA only if it improves the close.

Useful body shape:

```
[Core claim]

[The buyer situation this helps]

1. [Criterion or lesson]
[Why it matters]
[What to check or do]

2. [Criterion or lesson]
[Why it matters]
[What to check or do]

3. [Criterion or lesson]
[Why it matters]
[What to check or do]

[Synthesis]
[Optional CTA]
```

Quality rules:

- list items must be parallel and non-overlapping;
- do not invent a number just to create a numbered hook;
- avoid shallow one-line tips;
- do not hide one argument across unrelated points;
- use bullets instead of numbers when order does not matter.
<!-- /playbook-section -->

<!-- playbook-section:case_study_before_after -->
## Case Study / Before-After

Best for documented transformations, real client results, and sourced operating
changes. This is the highest-risk structure because it invites causal and
numeric overclaiming.

Required evidence:

- a documented starting state;
- the action or bridge;
- a documented ending state;
- any named metric, timeframe, client, or quote explicitly approved.

Use this sequence:

1. Hook with the documented contrast or result.
2. Establish the starting constraint.
3. Explain what changed in concrete terms.
4. Show the documented after-state.
5. Separate observation from causal inference.
6. Extract one transferable lesson.
7. Add the planned CTA.

Useful body shape:

```
[Documented before/after hook]

Before:
[Real starting state]

What changed:
- [Real action]
- [Real action]

After:
[Real ending state]

The lesson:
[One defensible operating principle]

[Optional CTA]
```

Quality rules:

- never fill a missing result with an estimate;
- never imply one change caused the whole result unless the source establishes
  that causal relationship;
- anonymize only when the source requires it, and do not add fake identifying
  detail;
- if either state is missing, switch structures.
<!-- /playbook-section -->

<!-- playbook-section:conversational_story -->
## Conversational Story

Best for founder moments, focused lessons, trend reactions, and direct operator
POV. "Story" means a coherent narrative thread, not permission to invent a
scene.

Use this sequence:

1. Open with the claim, concrete moment, or tension.
2. Give only the context needed to understand it.
3. Reveal the constraint, mistake, disagreement, or shift.
4. Develop the insight in short, natural paragraphs.
5. Explain what the target buyer should notice or do differently.
6. Close on conviction or the planned CTA.

Useful body shape:

```
[Direct hook]

[Specific context]

[What made the situation difficult or surprising]

[The insight]

[What changes for the reader]

[Conviction or optional CTA]
```

Quality rules:

- first-person details must come from the source;
- do not manufacture dialogue, emotions, chronology, or sensory detail;
- keep the middle moving; do not repeat the lesson in several forms;
- TrendCard posts should sound like analysis, not a fabricated founder memory;
- a short story is stronger than a padded confession.
<!-- /playbook-section -->
